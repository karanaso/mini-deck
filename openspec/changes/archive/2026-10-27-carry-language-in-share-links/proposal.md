# Proposal

## Why

Share links currently carry the deck and capability token but not the interface language. A Greek editor who shares a deck with a collaborator whose browser prefers English sends them into an English interface, even though both are looking at the same deck. The first rendered UI language should match the language in which the link was created, while each collaborator remains free to switch afterward.

## What Changes

- Add an interface-language hint to every edit and view link generated by the share dialog: `/d/{deckId}?lang={en|el}#{token}`. The token remains in the fragment and the deck URL remains the authorization boundary.
- On opening a deck link with a valid `lang`, make that language the initial interface language before the first render, taking precedence over a previously stored locale cookie and the browser's `Accept-Language`.
- Persist the link's language as the visitor's locale preference, so reloads and later deck links stay in that language until the collaborator switches language themselves.
- Ignore missing or invalid `lang` values and fall back to the existing resolution order: stored locale, then browser preference, then English. Existing `/d/{deckId}#{token}` links without a language keep working unchanged.
- Keep the locale parameter purely presentational. It MUST NOT influence the token, role, permissions, deck identity, collaboration data, exported content, or recent-deck entries.
- Update the existing `ui-localization` contract, which currently forbids language in deck links, and document/test the new share-link behavior.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `ui-localization`: Share-link creation carries the active interface locale; a valid link locale becomes the initial and remembered locale; the old "language never appears in deck links" invariant is replaced by "link language never affects authorization or capability tokens."

## Impact

- **Web share flow**: `buildDeckLinks` and the share dialog include the active locale in edit and view links; changing language while the dialog is open updates the generated links.
- **Request handling**: the existing Next.js proxy consumes a valid `lang` parameter on deck routes, applies the locale before rendering, and removes the parameter from the address bar without losing the fragment token.
- **Localization**: resolution gains a link-locale step with precedence over the stored cookie and `Accept-Language`; the locale cookie remains the persistence mechanism.
- **Tests and docs**: unit coverage for link construction and proxy handling plus Playwright coverage for first-open language, precedence, persistence, invalid values, view links, and old links; update `docs/localization.md` and `docs/sharing.md`.
- **Compatibility**: old links, capability tokens, API envelopes, database schema, collaboration documents, and exported content are unchanged. A recipient's stored language preference may be replaced when they open a language-bearing link, by design.
- **Dependency**: this is a stacked planning change. `add-greek-localization` introduces the `ui-localization` capability but is not yet archived, so its spec must be synced or archived before this change's delta is applied. This change supersedes that change's "language is kept out of deck URLs" requirement.
